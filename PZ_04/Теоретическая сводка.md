# От двумерной карты к графу

## 1. Постановка задачи

Пусть имеется двумерное поле:

```text
S . . . # .
. # . . # .
. # . . . .
. . . # . G
```

Необходимо найти путь из `S` в `G`, не проходя через препятствия `#`.

На первый взгляд это задача работы с двумерным массивом. Алгоритмически удобнее рассматривать её как задачу на **графе**.

---

## 2. Что такое граф в данном контексте

Каждая проходимая клетка:

```python
(row, col)
```

является **вершиной графа**.

Если из одной клетки разрешено перейти в другую, между ними существует **ребро**.

Для движения по четырём направлениям:

```text
      (r-1, c)
          ↑
(r,c-1) ← (r,c) → (r,c+1)
          ↓
      (r+1, c)
```

Явно создавать объект `Graph` необязательно. Граф можно задавать **неявно** через функцию соседей.

---

## 3. Функция neighbors

```python
DIRECTIONS = [
    (-1, 0),
    (1, 0),
    (0, -1),
    (0, 1),
]
```

Для текущей клетки:

```python
row, col = current
```

получаем кандидата:

```python
nr = row + dr
nc = col + dc
```

После этого проверяем:

1. находится ли клетка внутри карты;
2. не является ли она препятствием.

Идея функции:

```python
def get_neighbors(node, grid):
    ...
```

важна архитектурно. Алгоритм поиска не должен знать, как карта нарисована. Он должен уметь ответить только на вопрос:

> В какие вершины можно перейти из текущей?

# Как восстановить найденный путь

## 4.

Предположим, алгоритм достиг GOAL. Это означает, что цель найдена, но последовательность клеток маршрута ещё не восстановлена.

Поэтому при переходе:

```text
current → next_node
```

нужно сохранять:

```python
came_from[next_node] = current
```

Пример:

```text
S → A → B → C → G
```

В памяти хранится:

```text
A ← S
B ← A
C ← B
G ← C
```

---

## 5. Восстановление маршрута

Начинаем с GOAL:

```python
current = goal
path = []
```

И движемся по `came_from`:

```python
while current != start:
    path.append(current)
    current = came_from[current]
```

После добавления START маршрут будет записан в обратном порядке, поэтому:

```python
path.reverse()
```

---

## 6. Почему `came_from` универсален

Этот механизм одинаково применим к:

- BFS;
- Dijkstra;
- A*.

Меняется правило выбора следующей клетки, но восстановление маршрута остаётся практически одинаковым.

Это важный пример отделения общей логики от конкретного алгоритма.

---

# BFS — поиск в ширину

## 7. Основная идея BFS

BFS — Breadth-First Search — исследует вершины **слоями**.

Для старта:

```text
        2
      1 1 1
    2 1 S 1 2
      1 1 1
        2
```

Сначала рассматриваются клетки на расстоянии одного шага, затем двух, затем трёх и так далее.

---

## 8. Почему используется очередь

BFS использует FIFO:

```text
First In — First Out
```

В Python удобно применять:

```python
from collections import deque
```

Начальное состояние:

```python
queue = deque([start])
visited = {start}
```

Извлекаем старейший элемент:

```python
current = queue.popleft()
```

Новых соседей добавляем в конец:

```python
queue.append(next_node)
```

---

## 9. Основная схема BFS

```python
from collections import deque

queue = deque([start])
visited = {start}
came_from = {}

while queue:

    current = queue.popleft()

    if current == goal:
        break

    for next_node in get_neighbors(current, grid):

        if next_node in visited:
            continue

        visited.add(next_node)
        came_from[next_node] = current
        queue.append(next_node)
```

---

## 10. Почему BFS находит кратчайший путь

Если каждый переход имеет одинаковую стоимость:

```text
1 шаг = стоимость 1
```

BFS рассматривает клетки в порядке увеличения количества шагов от старта.

Поэтому первая найденная цель имеет минимальное число переходов.

---

## 11. Ограничение BFS

Пусть существуют клетки:

```text
обычная       стоимость 1
болото        стоимость 8
```

BFS не учитывает стоимость. Для него каждая новая клетка — просто один шаг.

Поэтому путь из 6 дешёвых клеток может быть выгоднее пути из 4 дорогих, но BFS этого не различает.

---

## 12. Сложность BFS

Для графа:

```text
V — число вершин
E — число рёбер
```

временная сложность:

```text
O(V + E)
```

Для сетки с фиксированным числом соседей это фактически линейно относительно числа доступных клеток.

Память:

```text
O(V)
```

поскольку необходимо хранить очередь, посещённые вершины и `came_from`.

---

# Dijkstra — путь минимальной стоимости

## 13. Почему нужен Dijkstra

Рассмотрим:

```text
S M M G
. . . .
```

где:

```text
. — стоимость 1
M — стоимость 5
```

Верхний путь короче по числу клеток:

```text
S → M → M → G
```

но дорогой.

Нижний путь длиннее, однако может иметь меньшую суммарную стоимость.

Следовательно:

> минимальное число шагов и минимальная стоимость — разные задачи.

---

## 14. Накопленная стоимость

Dijkstra хранит:

```python
cost_so_far[node]
```

Это минимальная известная стоимость пути:

```text
START → node
```

Для старта:

```python
cost_so_far[start] = 0
```

Для соседа:

```python
new_cost = (
    cost_so_far[current]
    + movement_cost(next_node)
)
```

Если `new_cost` лучше ранее известной стоимости, данные для вершины обновляются.

---

## 15. Приоритетная очередь

BFS выбирает:

```text
кто раньше пришёл в очередь
```

Dijkstra выбирает:

```text
у кого сейчас минимальная накопленная стоимость
```

Поэтому нужна priority queue.

В Python:

```python
import heapq
```

Добавление:

```python
heapq.heappush(frontier, (priority, node))
```

Извлечение минимального:

```python
priority, current = heapq.heappop(frontier)
```

---

## 16. Схема Dijkstra

```python
frontier = [(0, start)]

cost_so_far = {
    start: 0
}

came_from = {}

while frontier:

    current_cost, current = heapq.heappop(frontier)

    if current == goal:
        break

    for next_node in get_neighbors(current, grid):

        new_cost = (
            cost_so_far[current]
            + movement_cost(next_node)
        )

        if (
            next_node not in cost_so_far
            or new_cost < cost_so_far[next_node]
        ):
            cost_so_far[next_node] = new_cost
            came_from[next_node] = current

            heapq.heappush(
                frontier,
                (new_cost, next_node),
            )
```

---

## 17. Почему вершина может попасть в heap несколько раз

`heapq` не предоставляет простой операции уменьшения приоритета уже существующего элемента.

Практический подход — добавить новую запись с улучшенной стоимостью. При извлечении устаревшую запись можно пропустить.

Такой подход часто используется в учебных и прикладных реализациях Dijkstra и A* на Python.

---

## 18. Ограничение Dijkstra

Алгоритм предполагает:

```text
все стоимости переходов неотрицательны
```

При отрицательных весах его стандартная логика перестаёт гарантировать оптимальный результат.

В нашей задаче стоимости клеток положительны, поэтому Dijkstra применим.

---

# A* — направленный поиск

## 19. Недостаток Dijkstra

Dijkstra знает:

```text
сколько уже стоил путь
```

но не использует информацию:

```text
где находится цель
```

Поэтому поиск может распространяться во многие стороны.

A* добавляет оценку оставшегося расстояния до цели.

---

## 20. Три величины A*

Для вершины `n`:

```text
g(n)
```

— фактическая стоимость пути от START до `n`;

```text
h(n)
```

— эвристическая оценка стоимости пути от `n` до GOAL;

```text
f(n)
```

— оценка полного маршрута через `n`.

Формально:

```text
f(n) = g(n) + h(n)
```

---

## 21. Manhattan distance

При движении только:

```text
↑ ↓ ← →
```

естественная эвристика:

```python
def heuristic(a, b):
    return (
        abs(a[0] - b[0])
        + abs(a[1] - b[1])
    )
```

Это Manhattan distance.

Например, перейти из:

```text
(2, 3)
```

в:

```text
(5, 7)
```

при отсутствии препятствий минимально нужно:

```text
|5 - 2| + |7 - 3|
= 3 + 4
= 7 шагов
```

---

## 22. Приоритет в A*

Для соседа сначала вычисляется реальная накопленная стоимость:

```python
new_cost = (
    cost_so_far[current]
    + movement_cost(next_node)
)
```

Затем приоритет:

```python
priority = (
    new_cost
    + heuristic(next_node, goal)
)
```

То есть A* предпочитает клетки, для которых сочетаются:

```text
небольшая уже накопленная стоимость
+
перспективное положение относительно цели
```

---

## 23. A* и Dijkstra

Если:

```text
h(n) = 0
```

для всех вершин, A* фактически превращается в Dijkstra.

Поэтому A* можно рассматривать как Dijkstra, дополненный информацией о направлении к цели.

---

## 24. Допустимая эвристика

Чтобы A* гарантированно находил оптимальный путь, эвристика не должна завышать реальную минимальную стоимость до цели.

Такую эвристику называют **допустимой (admissible)**.

Для движения по четырём направлениям с минимальной стоимостью шага 1 Manhattan distance является естественным выбором.

Главная идея для студента:

> эвристика должна направлять поиск, но не должна переоценивать минимальную оставшуюся стоимость.

# Как визуализировать поиск в PyGame

## 25. Почему обычный цикл поиска не подходит

Если внутри одного кадра выполнить:

```python
while frontier:
    ...
```

алгоритм может полностью завершиться до следующего:

```python
pygame.display.flip()
```

Пользователь увидит только:

```text
исходная карта
↓
готовый путь
```

Процесс поиска будет потерян.

---

## 26. Генератор как источник шагов

Для пошаговой визуализации удобно использовать `yield`.

Например:

```python
def bfs_steps(...):

    while queue:

        current = queue.popleft()

        yield {
            "type": "visit",
            "node": current,
        }
```

После `yield` функция приостанавливается.

Следующий шаг выполняется вызовом:

```python
step = next(generator)
```

---

## 27. Связь с главным циклом PyGame

Главный цикл приложения:

```python
while running:

    dt = clock.tick(60) / 1000.0

    handle_events()
    update(dt)
    render()
```

В `update()` можно контролировать частоту алгоритмических шагов:

```python
step_timer += dt

if searching and step_timer >= step_interval:

    step_timer = 0

    try:
        step = next(search_generator)

    except StopIteration:
        searching = False
```

Таким образом:

```text
PyGame:       60 кадров/с
Алгоритм:     например, 10 шагов/с
```

Это независимые скорости.

---

## 28. OPEN и CLOSED

Для визуализации удобно различать:

```text
OPEN
```

— вершина обнаружена и ожидает обработки;

```text
CLOSED
```

— вершина уже обработана.

Это прежде всего **алгоритмические состояния**, а цвет — только способ их представить.

Например:

```text
OPEN   → голубой
CLOSED → синий
PATH   → жёлтый
```

```text

```

Алгоритм работает с данными. Renderer показывает эти данные.

## 30. Что студент должен понимать перед началом работы

Логическая цепочка:

```text
сетка
↓
неявный граф
↓
соседи
↓
frontier
↓
came_from
↓
поиск
↓
восстановление пути
↓
визуализация
```

Различия алгоритмов:

```text
BFS
порядок определяется очередью FIFO
оптимален по числу шагов при одинаковой стоимости переходов

Dijkstra
приоритет определяется накопленной стоимостью
находит путь минимальной стоимости при неотрицательных весах

A*
приоритет = накопленная стоимость + эвристика
использует положение цели для более направленного поиска
```

# Краткий справочник

| Понятие | Назначение |
|---|---|
| `node` | клетка / вершина графа |
| `neighbors(node)` | допустимые переходы |
| `frontier` | вершины, ожидающие обработки |
| `visited / closed` | уже обработанные вершины |
| `came_from` | восстановление маршрута |

| `g(n)` | накопленная стоимость |
| `h(n)` | эвристика |
| `f(n)` | приоритет A* |
| `yield` | пауза алгоритма между шагами |
